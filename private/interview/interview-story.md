# 면접 스토리 가이드

## 핵심 한 줄

> "실유저를 모을 수 없는 서비스라서, LLM이 상황을 보고 판단하는 유저를 직접 만들었습니다."

---

## 왜 이걸 했는가 (동기)

Festin은 실제 축제에서만 쓰이는 서비스라 평소에 실유저가 없다.
유저 없이는 서비스의 문제를 발견할 수 없고, 발견 못 하면 개선도 없다.

k6 부하 테스트는 이미 블로그에 있는 내용이다.
더 근본적인 문제는, k6는 내가 이미 아는 것만 확인한다는 것이다.
"스크립트대로 요청을 N번 보낸다"에서 예상하지 못한 일은 일어나지 않는다.

그래서 **LLM이 현재 상황을 보고 직접 판단하는 에이전트**를 만들었다.
에이전트가 예상하지 못한 행동 시퀀스를 만들고, 거기서 비즈니스 문제가 발견된다.

---

## 무엇을 만들었는가 (구현)

### LLM이 판단하는 시점

매 API 호출마다 LLM을 부르지 않는다.
분기가 필요한 순간, 즉 인간의 판단이 필요한 포인트에만 LLM을 호출한다.
또한 순번이 바뀌지 않으면 대기 중 판단도 호출하지 않는다 — 호출 횟수와 비용 최소화.

```
부스 목록 조회 후 → "등록할까? 어디에?"
순번이 바뀌었을 때 → "기다릴까 / 취소할까 / 다른 부스 볼까?"
취소 후 → "재시도할까?"
```

### 페르소나

에이전트마다 다른 성격을 LLM 프롬프트에 주입한다.
같은 상황(순번 8, 5분 경과)을 보더라도:
- 급한 성격 → "취소하고 다른 부스 가겠다"
- 느긋한 성격 → "조금 더 기다려보겠다"
- 합리적인 성격 → "게임부스가 2명이니 옮기는 게 낫다"

이 다양성이 예상하지 못한 시퀀스를 만들어낸다.

엣지케이스 패턴(연타형, 네트워크 재시도형, 동시 탭형)은 **페르소나를 고정**한다.
이 패턴들의 핵심은 "등록하는 방식"이지 "등록 여부"가 아니기 때문에,
LLM이 exit을 결정하면 버그 탐지 코드에 도달하지 못한다.

### 유저 패턴 9종 (+ staff 고정 배치)

**정상 행동** (LLM 판단):
- 대기형(40%), 탐색형(20%), 이탈형(10%), 재시도형(10%)
- 유령 탐색형(7%), 유령 등록형(5%)

**엣지케이스** (페르소나 고정, 버그 탐지):
- 연타형(3%), 네트워크 재시도형(3%), 동시 탭형(2%)

**스태프**: 부스당 1명 고정. LLM 판단 없이 대기열 순서대로 호출.

### LLM 선택: Groq (llama-3.1-8b-instant)

처음에는 Gemini 2.5 Flash를 사용했으나 Phase 2 10명 시뮬레이션에서 257원이 발생했다.
Groq 무료 티어(500k TPD)로 전환 후 비용 $0로 동일 시뮬레이션 동작.

### 실제 배포 서버에 실제 API 호출

- 배포 서버: `api.festin.shop`
- asyncio + aiohttp로 에이전트 전원 동시 실행
- 결과를 findings-template.md에 기록

### 무인 운영 (Phase 4): cron + 이상치 자동 감지

DAU 1000 한 달치를 시간대별 "파동(wave)"으로 압축해, GitHub Actions cron으로 자동 반복 실행한다. wave마다 점심/오후/저녁 중 시간대를 골라 패턴 비율과 부스 인기도를 다르게 적용 → "점심 food 쏠림", "저녁 drink 연타"가 스크립트 없이 자연 발현된다.

각 wave 종료 후 `wave_report.py`가 지표를 요약하고 임계값(5xx>0, 버그>0, 이탈률>50%, 전환율<30%, LLM 환각>20%)을 넘으면 GitHub 어노테이션을 출력한다. **5xx가 있으면 워크플로우가 fail 처리돼, 내가 안 보고 있어도 장애 알림이 온다.**

## 무엇을 발견했는가 (결과)

### 발견 #1 — 스태프가 다음 손님을 부르지 못하고 있었다 (Phase 4) ★ 메인

**현상**: `call_next` 응답이 500인데 `queue_empty: false` 다. **큐에 사람이 있는데 호출이 실패**하고 있었다. 첫 wave 에서 100회 호출 중 **93회 실패**.

```json
{"agent_id": "w0001_a050", "pattern": "staff", "event": "call_next",
 "booth_id": 4, "status": 500, "queue_empty": false, "latency_ms": 46}
```

**원인 — 좀비 user_id 무한 루프**:

```
1. MySQL users 에 없는 좀비 user_id 가 Redis 대기열에 잔존
2. 호출 → dequeue → Soft Lock 생성 (원래 timestamp 보존)
3. MySQL INSERT → FK 위반 (SQLState 23000) → 500
4. 1분 뒤 복구 배치가 원래 순번 그대로 좀비를 되살림
↺ 반복 — 좀비 하나가 부스 하나를 영구 정지시킨다
```

Redis 가 대기열의 Primary Store 인데 MySQL `users` 와의 참조 무결성을 보장하는 장치가 없었다. 그리고 **정확한 순번 복구를 위한 Soft Lock 설계가, 여기서는 좀비를 정확하게 되살리는 방향으로 작동**했다.

**좀비 user_id 는 어떻게 생기나 — 정상 API 경로로 생긴다**:
- `JwtAuthenticationFilter` 는 DB 를 조회하지 않는다. 토큰에서 `userId` 를 꺼내 `SecurityContext` 에 넣을 뿐이다 (의존성은 `JwtTokenProvider` 하나)
- `EnqueueService` 는 `QueueCachePort`·`BoothCachePort` 만 의존한다. **등록 경로에 사용자 조회가 없다** — 발견 #1 에서 p99 를 위해 DB 접근을 걷어낸 그 결정의 연장선이다
- 토큰 무효화 장치(블랙리스트·로그아웃·리프레시)가 없고 JWT 수명은 **24시간** (`application.yml`: `expiration: 86400000`)
- `queue:booth:*` 에는 TTL 이 없고 Redis 는 `--appendonly yes` 로 영속화된다

> ⇒ **사용자 행이 MySQL 에서 사라져도, 만료 전 토큰이면 대기 등록이 성공한다.** 그렇게 들어간 `userId` 는 큐에 영구히 남는다.
> 즉 좀비는 데이터를 지워야 생기는 게 아니라, 인증이 stateless 인 한 정상 경로로 생긴다.

**비즈니스 임팩트**: 축제 현장에서 스태프가 "다음 손님 호출"을 눌러도 열에 아홉이 실패한다. 그 부스의 줄은 멈춘 채로 남고, 호출 자체가 실패했으니 노쇼 타임아웃(5분)도 걸리지 않는다.

**왜 k6로는 못 잡나**: `callnext-test.js` 는 `setup()` 에서 유저 100명을 새로 만들어 등록시킨 뒤 곧바로 호출한다. 유저가 전원 살아 있으니 좀비가 생길 수 없다. **이 버그는 유저가 사라진 뒤에야 존재하는 상태에서만 나타난다** — 매 실행을 깨끗한 상태에서 시작하는 부하 테스트로는 원리적으로 도달할 수 없다.

**수정 (2단계)**:
1. 응급 처치 — 대기열과 `users` 의 차집합을 ZREM 하는 정합성 복원을 시뮬레이션 시작 루틴에 편입(`5e6fe92`). 이후 wave 에서 `call_next` 100회 중 5xx **0회**.
2. 근본 해결 — 스크립트는 이미 생긴 좀비를 치울 뿐이라, 서버가 스스로 방어하도록 `CallNextService.dequeueCallableUser()` 에서 Soft Lock 을 만들기 전에 사용자 존재를 확인하고, `SoftLockRecoveryBatch` 에 좀비 Soft Lock 폐기(2차 방어)를 넣었다. 좀비를 심어 재현하는 Testcontainers 테스트 5종(`ZombieQueueCallNextTest`)으로 검증.

**함께 드러난 것 — 감시 체계의 맹점**: 당시 리포트는 "5xx 0건"으로 적고 있었는데, 사실은 **5xx 를 세는 지표 자체가 없었다.** 측정하지 않아서 0 이었던 것이다. 엔드포인트별 5xx 집계와 임계값 자동 알림을 추가했다(`1884d93`).

### 발견 #2 — net_retry 패턴에서 중복 등록 (Phase 2)

**현상**: 동일 부스에 500ms 간격으로 2회 요청 → 둘 다 `201 Created`

```json
{"statuses": [201, 201], "bug_detected": true}
```

**원인**: Lua 스크립트는 이미 중복을 잡아 `ALREADY_ENQUEUED` 를 반환하고 있었다. 큐 자체는 멱등했다. 다만 결과 변환 계층이 이를 신규 등록과 동일하게 취급해 컨트롤러가 늘 201 을 반환했다 — **도메인의 멱등성이 HTTP 계약까지 전달되지 않았던 것.**

**비즈니스 임팩트**: 큐와 데이터는 정상이므로 실제 피해는 제한적이다. 다만 클라이언트는 응답 코드로 상태를 판단하므로, 201 을 두 번 받은 앱은 서버(1건)와 다른 상태(2건)를 갖게 된다.

**수정**: 409 가 아니라 신규 201 / 기존 200 분기(`29dbe17`). 이후 Phase 4 동시성 패턴 49회 시도에도 중복 0건.

### 발견 #3 — 부스 쏠림 (Phase 4, 무인 운영)

**현상**: 점심 파동에서 대기열이 특정 부스로 쏠림. 부스 불균형 stdev 평균 16.6(최대 23.8), 변동계수 CV 최대 0.78 — 한 부스는 텅 비었는데 옆 부스는 줄이 길었다.

**측정**: 부스별 대기열 길이를 30초 간격으로 스냅샷 → wave마다 stdev/CV 집계.

**비즈니스 임팩트**: 5xx 를 잡고 난 뒤에도 남는 문제다. 서버가 멀쩡해도 운영 효율과 유저 경험이 깎인다. 한 부스 앞에 줄이 몰리는 동안 옆 부스 스태프는 논다.

**개선 방향**: 부스 추천/분산 유도 → 개선 전후 stdev 비교로 효과 수치화.

### 발견 #4 — 이탈은 생각보다 늦게 온다 (Phase 4)

**현상**: 평균 이탈 순번이 Phase 3 20.3번 → Phase 4 점심 파동 27.7번. 사람들은 27번째 순번까지 기다리다 포기했다. 이탈률 18.7%(5명 중 1명).

**왜 k6로는 안 나오나**: 이탈 순번이 시간대 맥락(점심엔 더 기다림)에 따라 변한 건, LLM이 상황을 보고 판단했기 때문이다. `if (queue > 5) cancel()` 스크립트로는 고정값밖에 안 나온다.

**개선 방향**: 이탈 순번 분포 → "몇 번째 순번부터 이탈 경고를 띄울지" UX 임계값을 데이터로 결정.

## 면접 질문별 답변 가이드

### "왜 k6를 안 쓰고 LLM을 썼나요?"

k6는 스크립트대로만 움직입니다. 그건 제가 이미 예상한 것만 확인하는 거예요.
이 시뮬레이션의 목적은 **제가 설계하지 않은 상황을 만들어내는 것**입니다.

예를 들어 LLM 에이전트는 순번을 확인한 뒤, 다른 부스 상황까지 고려해서
"저쪽이 더 빠르겠다"고 판단하고 이동합니다.
이 행동 시퀀스는 k6로는 나올 수 없고, 거기서 대기열 이동 시 발생하는
비즈니스 문제나 동시성 이슈가 발견됩니다.

### "LLM 비용이 비싸지 않나요?"

처음에는 Gemini 2.5 Flash를 사용했는데, 10명 시뮬레이션에서 257원이 나왔습니다.
두 가지 최적화를 했습니다.

첫째, 순번이 바뀌지 않으면 대기 중 LLM을 호출하지 않습니다 — 코드가 직접 "대기 유지"를 반환합니다.
둘째, Groq 무료 티어(500k TPD)로 전환했습니다. 현재 LLM 비용은 $0입니다.

### "이탈률은 어떻게 측정했나요?"

각 에이전트가 LLM에게 판단을 요청할 때 `reason` 필드를 기록합니다.
"취소"를 선택한 시점의 순번, 경과 시간, reason을 모아서
"어떤 조건에서 이탈이 발생하는가"를 분포로 분석합니다.

숫자의 정확도보다 **개선 전후 같은 조건으로 비교**하는 게 목적이어서,
상대적 변화가 개선 효과의 근거가 됩니다.

### "실제 유저 행동과 얼마나 비슷한가요?"

완벽히 재현할 수는 없습니다.
하지만 중요한 건 **실제처럼 보이는 것**이 아니라
**내가 설계하지 않은 예외 상황을 만들어내는 것**입니다.
LLM이 상황을 보고 내리는 판단은 제가 미리 짠 코드보다 훨씬 다양한 경로를 만들고,
그 경로에서 발견된 문제는 실제 유저가 겪을 수 있는 문제입니다.

### "실제로 발견한 문제가 있나요?"

가장 큰 건 **스태프 호출 API의 500**입니다. 큐에 사람이 있는데도 호출이 실패하고 있었고, 첫 wave에서 100회 중 93회가 실패했습니다. 원인은 Redis 대기열에 남은 좀비 user_id가 MySQL FK 위반을 일으키는 것이었는데, **Soft Lock 복구 배치가 그 좀비를 원래 순번으로 정확히 되살려 무한 루프**가 되고 있었습니다. 좀비를 치우는 정합성 복원 스크립트로 우선 0회를 만들고, 이어서 호출 시점에 사용자 존재를 확인하도록 서버 코드를 고쳐 좀비가 다시 생겨도 부스가 멈추지 않게 했습니다.

그 외에 Phase 2의 멱등성 계약 불일치(중복 등록 [201, 201]), Phase 4의 부스 쏠림(CV 0.78)과 이탈 순번 분포(평균 27.7번)가 있습니다.
→ findings-template.md / simulation-report-phase4.md 참조

### "그건 테스트 데이터를 지워서 생긴 문제 아닌가요?"

맞습니다. 좀비는 제가 시뮬레이션 유저를 수동 삭제하면서 생겼습니다. 다만 그게 드러낸 건 **Redis 대기열과 MySQL `users` 사이에 참조 무결성을 보장하는 장치가 아예 없다**는 사실입니다.

Festin에는 아직 탈퇴 기능이 없어 지금 프로덕션에는 재현 경로가 없습니다. 하지만 **탈퇴를 붙이는 순간 그대로 터집니다.** 공교롭게도 이전 프로젝트(Sooum)에서 신고자 탈퇴로 신고 내역이 사라지는 문제를 런칭 후에 겪었는데, 이번에는 같은 계열의 문제를 런칭 전에 만난 셈입니다.

그래서 스크립트로 좀비를 지우는 데서 멈추지 않고 **서버가 스스로 방어하도록** 고쳤습니다. 호출 시점에 Soft Lock을 **만들기 전에** 사용자 존재를 확인해서, 좀비는 Soft Lock 없이 폐기하고 다음 대기자로 진행합니다. **되살릴 대상 자체를 없앤 것**이라 배치가 복원할 게 없어지고, 큐가 빌 때까지만 반복하니 종료도 보장됩니다. 배치에도 같은 판단을 넣어 좀비 Soft Lock은 롤백하지 않고 폐기하는 2차 방어를 뒀습니다.

### "왜 등록 API에서 막지 않았나요?"

거기서 막으면 좀비가 애초에 큐에 들어오지 않으니 더 깔끔해 보입니다. **일부러 하지 않았습니다.**

등록은 이 서비스에서 가장 많이 호출되는 API고, 저는 그 API에서 `@Transactional`을 걷어내 p99를 14초에서 558ms로 줄인 적이 있습니다. 여기에 사용자 조회를 다시 넣으면 **제가 없앤 DB 접근을 가장 뜨거운 경로에 그대로 되돌리는** 셈입니다.

반면 호출(call_next)은 스태프 전용이고 부스당 수 초에 한 번입니다. **같은 검증을 여기 두면 사용자 응답 경로에는 영향이 0이면서 FK 위반은 똑같이 막힙니다.** 정합성 검증은 "가능한 한 이른 곳"이 아니라 "비용이 가장 싼 곳"에 두는 게 맞다고 판단했습니다.

### "수정 범위가 어느 정도였나요?"

포트를 먼저 정의해두는 헥사고날 구조라 이 정도로 끝났습니다.

| 계층 | 변경 |
|---|---|
| Port | `UserRepositoryPort.existsById()` 메서드 1개 |
| Adapter | `JpaUserAdapter` 3줄 |
| Application | `CallNextService`, `SoftLockRecoveryBatch` |
| Domain | **0** |
| 스키마 · 인프라 · API 계약 | **0** |

가용성 결함을 도메인도 인프라도 건드리지 않고 막았습니다. 아키텍처가 실제로 값을 하는 건 이런 순간이라고 생각합니다 — 포트 하나로 끝날 수정인지, 여러 계층을 헤집을 수정인지는 사고가 나고 나서야 드러나니까요.

검증은 좀비를 심어 재현하는 Testcontainers 테스트 5종으로 했습니다. 특히 **대조군**을 뒀는데, 실유저의 Soft Lock은 여전히 원래 순번으로 복구되는지를 확인합니다. 복구 기능을 죽이지 않고 좀비만 걸러낸다는 근거입니다. 전체 43개 중 실패 0(스킵 1), 회귀 0입니다.

### "서버가 안 터졌으면 의미 없는 거 아닌가요?"

사실 **터지고 있었는데 제가 못 보고 있었습니다.** 리포트에는 "5xx 0건"이라고 적혀 있었지만, 그때 metrics에는 5xx를 세는 필드 자체가 없었습니다. 측정하지 않아서 0이었던 거죠. 이걸 계기로 엔드포인트별 5xx 집계와 임계값 자동 알림을 붙였습니다.

그리고 5xx를 잡은 뒤에도 발견은 이어졌습니다. **부스 쏠림**과 **이탈 순번 27.7번** 같은 운영 기준선은 서버가 멀쩡할 때 나오는 값이고, 그게 다음 제품 개선의 출발점이 됩니다.

## 이력서 문구 예시

**프로젝트 설명**
> 실유저 없는 서비스의 한계를 극복하기 위해 LLM 기반 유저 시뮬레이션 시스템 설계 및 구현.
> LLM(Groq llama-3.1-8b)이 현재 상황(대기 순번, 경과 시간, 다른 부스 현황)을 보고 행동을 결정하는
> 에이전트 9종을 GitHub Actions cron으로 무인 반복 실행해, 상태가 누적돼야 드러나는 결함을 탐지.

**성과**
> - 스태프 호출 API 5xx 발견·수정 — Redis 대기열의 좀비 user_id가 FK 위반을 일으키고 복구 배치가 이를 되살리는 무한 루프로 부스 대기열이 정지. 정합성 복원 도입 후 **100회 호출 중 93회 실패 → 0회**
> - 감시 체계 맹점 보완 — "5xx 0건" 집계가 실은 5xx 미측정이었음을 확인, 엔드포인트별 5xx 집계 + 임계값 초과 시 워크플로우 fail 알림 구축
> - enqueue API 멱등성 계약 불일치 수정 (중복 등록 [201, 201] → 201/200 분기), 동시성 패턴 49회 시도 중복 0건으로 재검증
> - 무인 운영에서 운영 기준선 도출 — 부스 쏠림(CV 0.78)·이탈 순번 분포(평균 27.7번) → 부스 분산/이탈 경고 UX 개선 포인트
> - LLM 비용 최적화: 순번 미변동 시 호출 생략(77% 감소) + Gemini→Groq 전환으로 257원 → $0
