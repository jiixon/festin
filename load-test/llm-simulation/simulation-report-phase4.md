# LLM 에이전트 시뮬레이션 Phase 4: DAU 1000 운영 시뮬레이션

## 목표

Phase 1~3이 설계 검증과 피크 시뮬레이션이었다면, Phase 4는 **실제 운영에 가까운 시뮬레이션**이다.

- GitHub Actions 스케줄로 자동 반복 실행
- 피크 시간대(점심, 오후, 저녁) 트래픽 집중 패턴 구현
- Phase 3에서 남긴 숙제 해결

## Phase 3에서 넘어온 숙제

- [x] Groq `retry-after` 기반 재시도 로직 개선 — fallback 없이 LLM 판단으로만 동작
- [x] `concurrent` 패턴을 피크 시간 시나리오로 재설계 — 두 명이 동시에 같은 부스에 몰리는 상황
- [x] 부스별 대기열 불균형 지표 추가

### 숙제 1: `retry-after` 정확 대기

Phase 3에서 Groq rate limit에 걸리면 고정 backoff(1초 → 2초)로 3번 재시도했다. 문제는 Groq가 "4.14초 뒤에 다시 시도하라"고 알려줘도 1+2초만 기다리다 3번 다 실패하고 fallback("가장 짧은 줄 선택")으로 빠지는 것이었다. fallback은 시뮬레이션을 멈추진 않지만 **그 에이전트는 페르소나를 잃는다.**

해결: `gemini_client`가 Groq 응답의 `retry-after` 헤더를 우선 파싱하고, 없으면 에러 메시지의 `"try again in N.NNs"` 패턴을 fallback으로 읽어 **정확히** 그만큼 기다린다(30초 캡). Phase 4에서 LLM 환각(`booth_id_corrected`) 비율은 8개 wave 전부 **0%** — 페르소나 손실 없이 LLM 판단만으로 동작했다.

### 숙제 2: `concurrent` 패턴 재설계

Phase 3에서 `concurrent`(동시 탭) 패턴은 0건이었다. 응답 포맷 파싱 버그로 부스 목록을 못 가져와 등록 자체가 안 됐는데, 실패 사유를 안 남겨서 원인 추적도 불가능했다.

해결:
- 파동 코디네이터가 `assigned_booth_id`로 충돌 대상 부스를 지정할 수 있게 함
- `booths[0]` 고정 대신 유효 부스 중 랜덤 선택 → 자연스러운 충돌 분포
- 실패 시 skip 사유를 로깅

Phase 4에서 `concurrent_enqueue`는 wave당 정상적으로 발현됐고, 동시성 패턴(double_tap·concurrent·net_retry) 총 **49회 등록 시도에도 중복 등록/멱등성 버그 0건**이었다.

### 숙제 3: 부스 불균형 지표

부스별 대기열 길이의 표준편차(`stdev`)와 변동계수(`CV`)를 30초 간격으로 스냅샷해 wave마다 집계하는 `booth_imbalance` 메트릭을 추가했다. 이게 Phase 4의 **핵심 발견**으로 이어진다(아래).

## 설계 방향: 한 달치 부하를 파동으로 압축한다

DAU 1000을 한 달간 실제로 돌리려면 서버 비용도, 시간도 감당이 안 된다. 그래서 **누적 부하를 시간대별 "파동(wave)"으로 압축**했다.

- 파동마다 점심/오후/저녁 중 한 시간대(`band`)를 골라 실행
- 시간대별로 **패턴 비율**과 **부스 인기도**를 다르게 적용
  - 점심: `leaver` 비중↑, food 부스 쏠림
  - 오후: `waiter` 비중↑ (포토부스는 길어도 기다림)
  - 저녁: `double_tap` 비중↑, drink 부스 연타
- wave당 방문객 ~50명 + 스태프 5명, 도착을 180초에 걸쳐 spread

이렇게 하면 "점심엔 푸드트럭 폭주", "저녁엔 술부스 연타" 같은 시간대 특성이 스크립트 없이 **자연스럽게 발현**된다.

## 실행 구조: 무인 cron + 이상치 자동 감지

```
GitHub Actions (cron)
  → 시간대 band 선택
  → runner.py 실행 (파동 N개)
  → wave_report.py (요약 + 이상치 감지)   ← always()
  → artifact 업로드
```

핵심은 **사람이 안 봐도 이상을 잡아내는 것**이다. `wave_report.py`가 각 wave 종료 후 지표를 요약하고 임계값을 넘으면 GitHub 어노테이션을 출력한다.

| 조건 | 레벨 | 의미 |
|------|------|------|
| 5xx > 0 | `error` (워크플로우 fail) | 서버 에러 → 알림 |
| bugs > 0 | `error` | 멱등성/동시성 버그 |
| 이탈률 > 50% | `warning` | 서버 지연 의심 |
| 전환율 < 30% | `warning` | 처리 누락 의심 |
| LLM 환각 > 20% | `warning` | 프롬프트/모델 점검 |

`5xx > 0`이면 워크플로우가 fail 처리돼 GitHub가 알림을 보낸다. 즉 **장애가 나면 내가 안 보고 있어도 메일이 온다.**

## 발견: "에러 없음"은 결과가 아니다

8개 wave 동안 서버 에러도, 동시성 버그도 없었다. t3.micro 한 대가 점심 피크 파동을 안정적으로 받아냈다는 뜻이다. **하지만 그게 발견이 없다는 뜻은 아니다.**

### 발견 #1 — 부스 쏠림 (불균형 stdev 평균 16.6, 최대 23.8)

부스 불균형 지표를 처음 측정해 보니, 점심 시간대에 대기열이 **특정 부스로 심하게 쏠렸다.** 변동계수(CV)가 최대 0.78까지 튀었다 — 어떤 부스는 텅 비어 있는데 어떤 부스는 줄이 stdev 20 이상으로 길었다는 의미다.

원인은 시간대별 부스 인기도(점심 = food 쏠림)를 반영했기 때문인데, 이건 **실제 축제에서 그대로 일어날 문제**다. 한 부스 앞에 줄이 몰리는 동안 옆 부스 스태프는 놀고 있다. 서버는 멀쩡한데 **운영 효율과 유저 경험이 깎인다.** → 부스 추천/분산 유도 같은 제품 개선 포인트.

### 발견 #2 — 사람들은 생각보다 오래 기다리다 포기한다 (평균 이탈 순번 27.7번)

Phase 3의 평균 이탈 순번은 20.3번이었는데, Phase 4 점심 파동에서는 **27.7번**으로 올라갔다. 즉 27번째 순번까지 기다리다 포기한다. 이탈률 18.7%는 "5명 중 1명이 포기"라는 뜻이고, 이들이 포기하는 시점(순번)을 알면 **"몇 번째 순번부터 이탈 경고를 띄워야 하는가"** 같은 UX 임계값을 데이터로 정할 수 있다.

이 두 발견 모두 **k6로는 절대 안 나온다.** k6는 내가 짠 `if (queue > 5) cancel()` 조건대로만 움직이니까. 이탈 순번이 20→27로 변한 건 LLM이 시간대 맥락(점심엔 좀 더 기다림)을 보고 판단했기 때문이다.

## 동시성 집중 검증

| 패턴 | 검증 목표 | Phase 4 결과 |
|------|----------|-------------|
| `double_tap` | 연타 시 중복 등록 | 49회 시도 중 중복 0 |
| `concurrent` | 동시 탭 이중 호출 | 정상 발현, 버그 0 |
| `net_retry` | 네트워크 재전송 멱등성 | 중복 0 |

Phase 2에서 멱등성 계약(중복 enqueue 시 201 대신 200, `29dbe17`)을 맞춘 이후, 동시성 패턴이 자연 발생하는 운영 파동에서도 **멱등성이 깨지지 않음**을 무인 반복으로 확인했다.

## Phase 3 → Phase 4 지표 비교

| | Phase 3 (피크 100명) | Phase 4 (운영 파동) |
|---|---|---|
| 실행 방식 | 수동 1회 | GitHub Actions cron 무인 반복 |
| 누적 에이전트 | 100명 | 404명 (8 wave, 진행 중) |
| 전환율 | 87.0% | 55.9% |
| 이탈률 | 7.3% | 18.7% |
| 평균 이탈 순번 | 20.3번 | 27.7번 |
| 버그 탐지 | 0건 | 0건 |
| 신규 지표 | — | 부스 불균형(stdev/CV) |

> 전환율이 87% → 56%로 떨어지고 이탈률이 7% → 19%로 오른 건 **악화가 아니다.** Phase 3은 단일 피크였고, Phase 4는 시간대 쏠림·이탈형 비중↑을 반영한 운영 파동이라 더 현실적인 수치다. 오히려 "점심엔 5명 중 1명이 이탈한다"는 운영 기준선을 얻었다.

## 현재 상태와 한계

- 지금까지 누적된 8개 wave는 **전부 `lunch` band**다. 오후/저녁 파동은 아직 충분히 안 쌓였다 → drink 연타·포토부스 인내 패턴은 데이터가 더 필요.
- cron이 계속 도는 중이라 이 수치는 **운영 중 스냅샷**이다. wave가 쌓이면 band별 비교가 가능해진다.

## 다음

1. 오후/저녁 band 데이터 축적 → 시간대별 이탈/불균형 비교
2. 부스 불균형 발견을 제품 개선으로 연결 (분산 유도 → 개선 전후 stdev 비교)
3. 이탈 순번 분포 → 이탈 경고 UX 임계값 도출

Phase 4의 결론: **무인 운영 시뮬레이션은 "장애 감시"가 아니라 "운영 기준선 발견" 도구다.** 서버가 멀쩡해도 부스 쏠림과 이탈 패턴은 계속 나오고, 그게 다음 제품 개선의 출발점이 된다.
