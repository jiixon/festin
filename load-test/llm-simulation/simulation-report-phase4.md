# LLM 에이전트 시뮬레이션 Phase 4: DAU 1000 운영 시뮬레이션

## 목표

Phase 1~3이 설계 검증과 피크 시뮬레이션이었다면, Phase 4는 **실제 운영에 가까운 시뮬레이션**이다.

- GitHub Actions 스케줄로 자동 반복 실행
- 피크 시간대(점심, 오후, 저녁) 트래픽 집중 패턴 구현
- Phase 3에서 남긴 숙제 해결

## Phase 3에서 넘어온 숙제

- [x] Groq `retry-after` 기반 재시도 로직 개선 — fallback 없이 LLM 판단으로만 동작
- [x] `concurrent` 패턴을 피크 시간 시나리오로 재설계 — 두 명이 동시에 같은 부스에 몰리는 상황
- [x] 부스별 대기열 불균형 지표 추가

### 숙제 1: `retry-after` 정확 대기

Phase 3에서 Groq rate limit에 걸리면 고정 backoff(1초 → 2초)로 3번 재시도했다. 문제는 Groq가 "4.14초 뒤에 다시 시도하라"고 알려줘도 1+2초만 기다리다 3번 다 실패하고 fallback("가장 짧은 줄 선택")으로 빠지는 것이었다. fallback은 시뮬레이션을 멈추진 않지만 **그 에이전트는 페르소나를 잃는다.**

해결: `gemini_client`가 Groq 응답의 `retry-after` 헤더를 우선 파싱하고, 없으면 에러 메시지의 `"try again in N.NNs"` 패턴을 fallback으로 읽어 **정확히** 그만큼 기다린다(30초 캡). Phase 4에서 LLM 환각(`booth_id_corrected`) 비율은 8개 wave 전부 **0%** — 페르소나 손실 없이 LLM 판단만으로 동작했다.

### 숙제 2: `concurrent` 패턴 재설계

Phase 3에서 `concurrent`(동시 탭) 패턴은 0건이었다. 응답 포맷 파싱 버그로 부스 목록을 못 가져와 등록 자체가 안 됐는데, 실패 사유를 안 남겨서 원인 추적도 불가능했다.

해결:
- 파동 코디네이터가 `assigned_booth_id`로 충돌 대상 부스를 지정할 수 있게 함
- `booths[0]` 고정 대신 유효 부스 중 랜덤 선택 → 자연스러운 충돌 분포
- 실패 시 skip 사유를 로깅

Phase 4에서 `concurrent_enqueue`는 wave당 정상적으로 발현됐고, 동시성 패턴(double_tap·concurrent·net_retry) 총 **49회 등록 시도에도 중복 등록/멱등성 버그 0건**이었다.

### 숙제 3: 부스 불균형 지표

부스별 대기열 길이의 표준편차(`stdev`)와 변동계수(`CV`)를 30초 간격으로 스냅샷해 wave마다 집계하는 `booth_imbalance` 메트릭을 추가했다. 이게 Phase 4의 **핵심 발견**으로 이어진다(아래).

## 설계 방향: 한 달치 부하를 파동으로 압축한다

DAU 1000을 한 달간 실제로 돌리려면 서버 비용도, 시간도 감당이 안 된다. 그래서 **누적 부하를 시간대별 "파동(wave)"으로 압축**했다.

- 파동마다 점심/오후/저녁 중 한 시간대(`band`)를 골라 실행
- 시간대별로 **패턴 비율**과 **부스 인기도**를 다르게 적용
  - 점심: `leaver` 비중↑, food 부스 쏠림
  - 오후: `waiter` 비중↑ (포토부스는 길어도 기다림)
  - 저녁: `double_tap` 비중↑, drink 부스 연타
- wave당 방문객 ~50명 + 스태프 5명, 도착을 180초에 걸쳐 spread

이렇게 하면 "점심엔 푸드트럭 폭주", "저녁엔 술부스 연타" 같은 시간대 특성이 스크립트 없이 **자연스럽게 발현**된다.

## 실행 구조: 무인 cron + 이상치 자동 감지

```
GitHub Actions (cron)
  → 시간대 band 선택
  → runner.py 실행 (파동 N개)
  → wave_report.py (요약 + 이상치 감지)   ← always()
  → artifact 업로드
```

핵심은 **사람이 안 봐도 이상을 잡아내는 것**이다. `wave_report.py`가 각 wave 종료 후 지표를 요약하고 임계값을 넘으면 GitHub 어노테이션을 출력한다.

| 조건 | 레벨 | 의미 |
|------|------|------|
| 5xx > 0 | `error` (워크플로우 fail) | 서버 에러 → 알림 |
| bugs > 0 | `error` | 멱등성/동시성 버그 |
| 이탈률 > 50% | `warning` | 서버 지연 의심 |
| 전환율 < 30% | `warning` | 처리 누락 의심 |
| LLM 환각 > 20% | `warning` | 프롬프트/모델 점검 |

`5xx > 0`이면 워크플로우가 fail 처리돼 GitHub가 알림을 보낸다. 즉 **장애가 나면 내가 안 보고 있어도 메일이 온다.**

## 발견 #0 — 스태프가 다음 손님을 부르지 못하고 있었다 (call_next 5xx)

가장 큰 발견은 "에러가 없다"가 아니라, **에러를 세지 않고 있었다**는 것이었다.

원본 로그를 보면 `call_next` 응답이 500이면서 `queue_empty: false` 다. **큐에 사람이 있는데 호출이 실패**하고 있었다는 뜻이다. 첫 wave 에서는 100회 호출 중 93회가 실패했다.

```json
{"agent_id": "w0001_a050", "pattern": "staff", "event": "call_next",
 "booth_id": 4, "status": 500, "queue_empty": false, "latency_ms": 46}
```

### 원인: 좀비 user_id 무한 루프

```
1. MySQL users 에 없는 좀비 user_id 가 Redis 대기열에 잔존
2. 호출 → dequeue → Soft Lock 생성 (원래 timestamp 보존)
3. MySQL INSERT → FK 위반 (SQLState 23000) → 500
4. 1분 뒤 SoftLockRecoveryBatch 가 원래 순번 그대로 좀비를 되살림
↺ 좀비가 다시 큐 맨 앞 → 또 500 → 배치가 또 복원 …
```

Redis 가 대기열의 Primary Store 인데 MySQL `users` 와의 참조 무결성을 보장하는 장치가 **아무것도 없었다.** 그리고 정확한 순번 복구를 위해 timestamp 를 보존하도록 만든 Soft Lock 복구 배치가, 여기서는 **좀비를 정확하게 되살리는 방향으로** 작동했다. 자가 치유 장치가 자가 악화 장치가 된 셈이다.

좀비 하나가 큐 맨 앞을 막으면 **그 부스의 대기열은 영구 정지**한다. 호출 자체가 실패했으니 노쇼 타임아웃(5분)도 걸리지 않는다.

### 수정

**1단계 — 운영 정합성 복원 (즉시 조치)**

- `5e6fe92` (06-08) — 대기열과 `users` 의 차집합을 ZREM 하는 정합성 복원 스크립트, 시뮬레이션 시작 루틴에 편입
- `1884d93` (06-10) — 엔드포인트별 5xx 집계 + 임계값 자동 알림 추가 (**감시 맹점 보완**)

수정 후 wave #4 에서 `call_next` 100회 중 5xx **0회**.

**2단계 — 애플리케이션 레벨 근본 해결**

스크립트는 이미 생긴 좀비를 치울 뿐이다. 서버가 스스로 방어하도록 두 지점을 막았다.

- `CallNextService.dequeueCallableUser()` — Soft Lock 을 **만들기 전에** 사용자 존재를 확인한다. 좀비는 Soft Lock 없이 폐기하므로 **배치가 되살릴 대상 자체가 사라진다.** 폐기 후 다음 대기자로 진행하고, 큐가 빌 때까지만 반복하므로 종료가 보장된다.
- `SoftLockRecoveryBatch` — 호출 도중 사용자가 사라져 Soft Lock 이 남은 경우에도, 좀비면 **롤백하지 않고** 제거해 루프를 끊는다.

**등록(enqueue) 시점 검증은 의도적으로 기각했다.** 좀비를 원천 차단할 수 있지만, 등록은 최다 호출 API 이고 `@Transactional` 을 걷어내며 없앤 DB 접근을 가장 뜨거운 경로에 되돌리게 된다. 호출은 스태프 전용 저빈도 API 이므로, 같은 검증을 여기 두면 **사용자 응답 경로 영향 없이** FK 위반만 막는다.

변경 범위 — Port 메서드 1개(`UserRepositoryPort.existsById()`), Adapter 3줄, Application 2곳. **Domain · 스키마 · 인프라 · API 계약 변경 0.**

**검증** — `ZombieQueueCallNextTest` 5종 (Testcontainers). 대조군으로 실유저의 Soft Lock 은 여전히 원래 순번으로 복구되는지까지 확인한다. 전체 43개 통과, 회귀 0.

```
[좀비 대기자] 폐기 후 호출 진행 - boothId: 5, 폐기: 2건, 호출: 3
[Soft Lock 배치] 보정 완료 - 스캔: 1, 복구: 0, 좀비 폐기: 1   ← 좀비: 되살리지 않음
[Soft Lock 배치] 보정 완료 - 스캔: 1, 복구: 1, 좀비 폐기: 0   ← 실유저: 기존대로 복구
```

### 왜 k6 로는 못 잡았나

`callnext-test.js` 는 `setup()` 에서 유저 100명을 새로 만들어 등록시킨 뒤 곧바로 호출하고 teardown 한다. 유저가 전원 살아 있으므로 좀비가 생길 수 없다. **이 버그는 유저가 사라진 뒤에야 존재하는 상태에서만 나타난다** — 상태가 누적돼야 재현되므로, 매 실행을 깨끗한 상태에서 시작하는 부하 테스트로는 도달할 수 없다.

## 발견: 서버 에러 외에도 계속 나온다

5xx 를 잡고 난 뒤에도 발견은 이어졌다. 다음 둘은 **서버가 멀쩡할 때 나온** 운영·UX 문제다.

### 발견 #1 — 부스 쏠림 (불균형 stdev 평균 16.6, 최대 23.8)

부스 불균형 지표를 처음 측정해 보니, 점심 시간대에 대기열이 **특정 부스로 심하게 쏠렸다.** 변동계수(CV)가 최대 0.78까지 튀었다 — 어떤 부스는 텅 비어 있는데 어떤 부스는 줄이 stdev 20 이상으로 길었다는 의미다.

원인은 시간대별 부스 인기도(점심 = food 쏠림)를 반영했기 때문인데, 이건 **실제 축제에서 그대로 일어날 문제**다. 한 부스 앞에 줄이 몰리는 동안 옆 부스 스태프는 놀고 있다. 서버는 멀쩡한데 **운영 효율과 유저 경험이 깎인다.** → 부스 추천/분산 유도 같은 제품 개선 포인트.

### 발견 #2 — 사람들은 생각보다 오래 기다리다 포기한다 (평균 이탈 순번 27.7번)

Phase 3의 평균 이탈 순번은 20.3번이었는데, Phase 4 점심 파동에서는 **27.7번**으로 올라갔다. 즉 27번째 순번까지 기다리다 포기한다. 이탈률 18.7%는 "5명 중 1명이 포기"라는 뜻이고, 이들이 포기하는 시점(순번)을 알면 **"몇 번째 순번부터 이탈 경고를 띄워야 하는가"** 같은 UX 임계값을 데이터로 정할 수 있다.

이 두 발견 모두 **k6로는 절대 안 나온다.** k6는 내가 짠 `if (queue > 5) cancel()` 조건대로만 움직이니까. 이탈 순번이 20→27로 변한 건 LLM이 시간대 맥락(점심엔 좀 더 기다림)을 보고 판단했기 때문이다.

| | Phase 3 (피크 100명) | Phase 4 (운영 파동) |

| 실행 방식 | 수동 1회 | GitHub Actions cron 무인 반복 |
| 누적 에이전트 | 100명 | 404명 (8 wave, 진행 중) |
| 전환율 | 87.0% | 55.9% |

| 서버 에러(5xx) | 미측정 | **244건 발견 → 수정 후 0건** |

## 현재 상태와 한계

- 지금까지 누적된 8개 wave는 **전부 `lunch` band**다. 오후/저녁 파동은 아직 충분히 안 쌓였다 → drink 연타·포토부스 인내 패턴은 데이터가 더 필요.
- cron이 계속 도는 중이라 이 수치는 **운영 중 스냅샷**이다. wave가 쌓이면 band별 비교가 가능해진다.
- **5xx 수정 후 데이터는 wave #4(06-07) 1건뿐이다.** 재발 없음을 주장하려면 수정 이후 wave를 더 쌓아야 한다.
- 좀비 user_id는 시뮬레이션 유저를 수동 삭제하며 발생했다. Festin에는 아직 탈퇴 기능이 없어 **당시 프로덕션에는 재현 경로가 없었지만, 탈퇴를 추가하는 순간 동일하게 터졌을 것**이다. 애플리케이션 레벨 방어를 넣은 지금은 추가해도 막힌다.
- 애플리케이션 방어의 근거는 **단위 테스트(Testcontainers)** 다. 좀비를 심은 상태로 프로덕션 wave를 다시 돌린 실측은 아직 없다 → 다음 wave에서 "좀비 N개 잔존 상태에서 호출 성공률" 을 측정하면 더 강한 근거가 된다.

## 다음

1. 오후/저녁 band 데이터 축적 → 시간대별 이탈/불균형 비교
2. 부스 불균형 발견을 제품 개선으로 연결 (분산 유도 → 개선 전후 stdev 비교)
3. 이탈 순번 분포 → 이탈 경고 UX 임계값 도출

Phase 4의 결론: **부하 테스트가 검증하는 건 "지금 이 순간의 서비스"다.** 매 실행을 깨끗한 상태에서 시작하기 때문이다. 하지만 장애는 대개 시간이 지나며 누적된 상태에서 나온다 — `call_next` 5xx가 정확히 그런 버그였다.

그리고 이 시뮬레이션은 장애가 없을 때도 쓸모가 있다. 서버가 멀쩡해도 부스 쏠림과 이탈 순번 같은 **운영 기준선**은 계속 나오고, 그게 다음 제품 개선의 출발점이 된다.

마지막으로 남는 교훈 하나: **"5xx 0건"이라고 적혀 있었지만 5xx를 세는 지표 자체가 없었다.** 측정하지 않은 것은 관측되지 않고, 관측되지 않은 것은 없는 것처럼 보인다. 감시 체계를 만들 때는 "무엇을 세고 있는가"를 먼저 확인해야 한다.
