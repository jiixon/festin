# 시뮬레이션 발견 기록

## 이 파일의 목적

시뮬레이션을 돌리면서 발견한 **비즈니스 문제**와 **기술 문제**를 기록하고,
개선 전후를 비교해서 서비스 성장을 수치로 증명한다.

이력서 스토리:
> "유저가 없어서 LLM으로 에이전트를 시뮬레이션했습니다.
> [발견한 문제]를 발견했고, [개선]을 통해 [지표]가 X% 개선됐습니다."

## 추적할 비즈니스 지표

| 지표 | 설명 | 측정 방법 |
|------|------|---------|
| **이탈률** | 등록 후 취소한 유저 비율 | cancel / enqueue |
| **전환율** | 탐색 후 등록까지 한 유저 비율 | enqueue / browse |
| **평균 이탈 순번** | 몇 번째 순번에서 포기하는가 | 이탈 시점 position 평균 |
| **부스 불균형 지수** | 부스별 대기열 편차 | 표준편차 |
| **유령 유저 비율** | 취소 없이 사라진 유저 비율 | ghost / total |
| **재시도율** | 이탈 후 다른 부스 재등록 비율 | retrier cancel → retry |
| **피크 처리율** | 스태프 호출 성공률 | called / enqueued |

### [발견 #1] net_retry 패턴에서 동일 부스 중복 등록 성공

**날짜**: 2026-04-20
**시뮬레이션 단계**: Phase 2 (14명)
**유형**: 기술 버그 — 동시성 / 멱등성

**발견한 것**:
> `net_retry` 패턴 에이전트(agent_009)가 동일 부스(booth_id=4)에 500ms 간격으로 등록 요청을 2번 보냈을 때
> 두 요청 모두 `201 Created`를 반환했다.

```json
{
  "agent_id": "agent_009",
  "pattern": "net_retry",
  "event": "net_retry_enqueue",
  "booth_id": 4,
  "statuses": [201, 201],
  "bug_detected": true
}
```

**수치**:
- 재현율: 1/1 (Phase 2 실행에서 100% 재현)

**원인 분석**:
> 네트워크 타임아웃 시 클라이언트가 동일 요청을 재전송하는 시나리오.
> **Lua 스크립트는 이미 중복을 감지해 `ALREADY_ENQUEUED(2)` 를 반환하고 있었다 — 큐 자체는 멱등했다.**
> 다만 `EnqueueResultFactory` 가 이를 정상 등록과 동일하게 변환해
> 컨트롤러가 항상 201 을 반환했다. 도메인의 멱등성이 HTTP 계약까지 전달되지 않은 것.

**비즈니스 임팩트**:
> 큐와 데이터는 정상이므로 실제 피해는 제한적이다(대기열이 부풀지 않는다).
> 다만 클라이언트는 응답 코드로 상태를 판단하므로, 201 을 두 번 받은 앱은
> 서버(1건)와 다른 상태(2건)를 갖게 된다.

**개선 방향**:
> 409 는 부적절하다 — 멱등성의 의미는 "같은 요청 → 같은 상태"이므로
> 이미 등록된 유저는 에러가 아니라 "이미 등록돼 있고 N번" 을 받아야 한다.
> **신규 201 / 기존 200 분기.**

**개선 후 재측정**:
- `[201, 201, 201]` → `[201, 200, 200]`, `bug_detected: false` (`29dbe17`)
- Phase 4 동시성 패턴(double_tap·concurrent·net_retry) 누적 49회 시도 중복 **0건**

### [발견 #2] call_next 5xx — 좀비 user_id 무한 루프 ★ 메인

**날짜**: 2026-06-08
**시뮬레이션 단계**: Phase 4 (무인 반복 운영)
**유형**: 기술 버그 — 정합성 / 가용성 (심각)

**발견한 것**:
> staff 의 `call_next` 응답이 500 인데 `queue_empty: false` 였다.
> **큐에 사람이 있는데 호출이 실패**하고 있었다.

```json
{"agent_id": "w0001_a050", "pattern": "staff", "event": "call_next",
 "booth_id": 4, "status": 500, "queue_empty": false, "latency_ms": 46}
```

**수치**:
- wave #1(05-28): `call_next` 100회 중 **93회 실패 (93%)**
- 수정 전 누적: 292회 중 244회 실패 (83.6%)
- 수정 후 wave: 100회 중 **0회**

**원인 분석**:
```
1. MySQL users 에 없는 좀비 user_id 가 Redis 대기열에 잔존
2. 호출 → dequeue → Soft Lock 생성 (원래 timestamp 보존)
3. MySQL INSERT → FK 위반 (SQLState 23000) → 500
4. 1분 뒤 SoftLockRecoveryBatch 가 원래 순번 그대로 좀비를 되살림
↺ 좀비가 다시 큐 맨 앞 → 또 500 → 배치가 또 복원 …
```
> Redis 가 대기열의 Primary Store 인데 MySQL `users` 와의 참조 무결성을 보장하는 장치가 없었다.
> **정확한 순번 복구를 위한 Soft Lock 설계가, 여기서는 좀비를 정확하게 되살리는 방향으로 작동**했다.

**비즈니스 임팩트**:
> 좀비 하나가 큐 맨 앞을 막으면 **그 부스의 대기열은 영구 정지**한다.
> 스태프가 "다음 손님 호출" 을 눌러도 열에 아홉이 실패하고,
> 호출 자체가 실패했으니 노쇼 타임아웃(5분)도 걸리지 않아 방치된다.

**왜 k6 로는 못 잡나**:
> `callnext-test.js` 는 `setup()` 에서 유저 100명을 새로 만들어 등록시킨 뒤 곧바로 호출하고 teardown 한다.
> 유저가 전원 살아 있으므로 좀비가 생길 수 없다.
> **이 버그는 유저가 사라진 뒤에야 존재하는 상태에서만 나타난다** — 상태가 누적돼야 재현되므로
> 매 실행을 깨끗한 상태에서 시작하는 부하 테스트로는 원리적으로 도달할 수 없다.

**개선 후 재측정**:
- `5e6fe92` 대기열과 `users` 차집합 ZREM → 시뮬레이션 시작 루틴 편입
- `call_next` 5xx: **93/100 → 0/100**

**근본 해결 (애플리케이션 레벨)**:

스크립트는 이미 생긴 좀비를 치울 뿐이라, 서버가 스스로 방어하도록 고쳤다.

1. **호출 시점 차단** — `CallNextService.dequeueCallableUser()`
   Soft Lock 을 **만들기 전에** 사용자 존재를 확인한다.
   좀비는 Soft Lock 없이 폐기 → **배치가 되살릴 대상 자체가 없어진다.**
   폐기 후 다음 대기자로 계속 진행하므로 좀비가 몇이든 부스는 멈추지 않고,
   큐가 빌 때까지만 반복하므로 종료가 보장된다.

2. **배치 2차 방어** — `SoftLockRecoveryBatch`
   호출 도중 사용자가 사라져 Soft Lock 이 남은 경우에도,
   좀비면 **롤백하지 않고** Soft Lock 만 제거해 루프를 끊는다.

**검증을 어디에 둘지의 트레이드오프**:
> 등록(enqueue) 시점에 검증하면 좀비가 애초에 들어오지 않는다. **기각했다.**
> 등록은 최다 호출 API 이고, `@Transactional` 을 걷어내며 없앤 DB 접근을
> 가장 뜨거운 경로에 되돌리는 셈이라 p99 개선을 스스로 무너뜨린다.
> 호출(call_next)은 스태프 전용 저빈도 API 이므로, 같은 검증을 여기 두면
> **사용자 응답 경로에 영향 없이** FK 위반만 막을 수 있다.

**변경 범위** (포트를 먼저 정의해둔 구조의 효과):

| 계층 | 변경 |
|---|---|
| Port | `UserRepositoryPort.existsById()` 메서드 1개 |
| Adapter | `JpaUserAdapter` 3줄 |
| Application | `CallNextService`, `SoftLockRecoveryBatch` |
| Domain | **0** |
| 스키마 · 인프라 · API 계약 | **0** |

**회귀 테스트**: `ZombieQueueCallNextTest` 5종 (Testcontainers)
- 좀비가 큐 맨 앞이어도 뒤의 실유저가 정상 호출
- 좀비는 Soft Lock 을 남기지 않음
- 폐기된 좀비가 배치 실행 후에도 되살아나지 않음
- 좀비 Soft Lock 이 남아도 배치가 롤백하지 않음
- **[대조군]** 실유저의 Soft Lock 은 기존대로 원래 순번으로 복구

> 전체 스위트 43개 통과, 회귀 0.
> 배치 로그가 두 분기를 그대로 보여준다 —
> `스캔: 1, 복구: 0, 좀비 폐기: 1` (좀비) / `스캔: 1, 복구: 1, 좀비 폐기: 0` (실유저)

> Festin 에는 아직 탈퇴 기능이 없어 현재 프로덕션에는 재현 경로가 없지만, **탈퇴를 추가하는 순간 동일하게 터졌을 것**이다. 지금은 추가해도 막힌다.

### [발견 #3] "5xx 0건" 은 측정하지 않아서 0 이었다

**날짜**: 2026-06-10
**시뮬레이션 단계**: Phase 4
**유형**: 계측 결함 — 감시 체계 맹점

**발견한 것**:
> Phase 4 리포트는 8개 wave 전부 `5xx = 0` 으로 집계하고 있었다.
> 그러나 당시 metrics 에는 **5xx 를 세는 필드 자체가 없었다.**
> 원본 wave JSON 을 재집계하니 `call_next` 5xx 가 244건이었다.

**비즈니스 임팩트**:
> 무인 감시를 만들어 두고도 정작 서버 에러를 놓치고 있었다.
> 측정하지 않은 것은 관측되지 않고, 관측되지 않은 것은 없는 것처럼 보인다.

**개선 후 재측정**:
- `1884d93` 엔드포인트별 5xx 카운트/누적 집계 추가
- `wave_report.py` 임계값 초과 시 GitHub 어노테이션 + **5xx > 0 이면 워크플로우 fail**
