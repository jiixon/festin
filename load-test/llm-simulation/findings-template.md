# 시뮬레이션 발견 기록

## 이 파일의 목적

시뮬레이션을 돌리면서 발견한 **비즈니스 문제**와 **기술 문제**를 기록하고,
개선 전후를 비교해서 서비스 성장을 수치로 증명한다.

이력서 스토리:
> "유저가 없어서 LLM으로 에이전트를 시뮬레이션했습니다.
> [발견한 문제]를 발견했고, [개선]을 통해 [지표]가 X% 개선됐습니다."

---

## 추적할 비즈니스 지표

| 지표 | 설명 | 측정 방법 |
|------|------|---------|
| **이탈률** | 등록 후 취소한 유저 비율 | cancel / enqueue |
| **전환율** | 탐색 후 등록까지 한 유저 비율 | enqueue / browse |
| **평균 이탈 순번** | 몇 번째 순번에서 포기하는가 | 이탈 시점 position 평균 |
| **부스 불균형 지수** | 부스별 대기열 편차 | 표준편차 |
| **유령 유저 비율** | 취소 없이 사라진 유저 비율 | ghost / total |
| **재시도율** | 이탈 후 다른 부스 재등록 비율 | retrier cancel → retry |
| **피크 처리율** | 스태프 호출 성공률 | called / enqueued |

### [발견 #1] net_retry 패턴에서 동일 부스 중복 등록 성공

**날짜**: 2026-04-20
**시뮬레이션 단계**: Phase 2 (14명)
**유형**: 기술 버그 — 동시성 / 멱등성

**발견한 것**:
> `net_retry` 패턴 에이전트(agent_009)가 동일 부스(booth_id=4)에 500ms 간격으로 등록 요청을 2번 보냈을 때
> 두 요청 모두 `201 Created`를 반환했다.

```json
{
  "agent_id": "agent_009",
  "pattern": "net_retry",
  "event": "net_retry_enqueue",
  "booth_id": 4,
  "statuses": [201, 201],
  "bug_detected": true
}
```

**수치**:
- 재현율: 1/1 (Phase 2 실행에서 100% 재현)

**원인 분석**:
> 네트워크 타임아웃 시 클라이언트가 동일 요청을 재전송하는 시나리오.
> 서버가 첫 번째 요청을 처리 완료했으나 응답 전에 연결이 끊기고,
> 클라이언트가 실패로 인식해 동일 요청을 재전송.
> 서버 enqueue 로직에 멱등성이 없어 두 번 모두 새 대기열 등록으로 처리됨.

**비즈니스 임팩트**:
> 실제 사용자가 앱 로딩이 느려 재시도했을 때 같은 부스에 2회 등록될 수 있음.
> 대기열 수가 실제보다 부풀려지고, 스태프가 같은 번호를 두 번 호출하는 상황 발생.

**개선 방향**:
> enqueue 시 동일 userId + boothId 조합 중복 체크 (Redis or DB unique constraint).
> 또는 요청 식별자(idempotency key)를 클라이언트에서 전달받아 서버에서 처리.

**개선 후 재측정**: (개선 후 채움)
