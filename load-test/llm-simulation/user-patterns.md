# 유저 행동 패턴 정의

## 핵심 개념

패턴은 에이전트의 **초기 성향**이다. 고정된 스크립트가 아니다.
LLM이 상황을 보고 판단하기 때문에, 같은 패턴이라도 상황에 따라 다르게 행동한다.

**LLM 판단 포인트** (정상 행동 패턴 공통):
1. 부스 목록을 보고 → "등록할까?"
2. 순번 확인 후 → "기다릴까 / 취소할까 / 다른 부스 볼까?"
3. 취소 후 → "재시도할까?"

패턴은 이 판단에 영향을 주는 **페르소나**로 LLM에 전달된다.

엣지케이스 패턴(double_tap, net_retry, concurrent)은 **등록 의사가 높은 페르소나를 고정**해서 사용한다.
LLM이 exit을 결정하면 버그 탐지 코드에 도달하지 못하기 때문이다.

> staff는 부스당 1명 고정 배치. 비율에 포함하지 않음.

| # | 패턴 | 코드명 | 비율 | 페르소나 성향 |
|---|------|--------|------|------------|
| 1 | 대기형 | `waiter` | **40%** | 인내심 높음, 기다리는 걸 선택. 느긋하거나 FOMO형 |
| 2 | 탐색형 | `explorer` | 20% | 여러 부스 비교 후 가장 짧은 줄에 등록 |
| 3 | 이탈형 | `leaver` | 10% | 인내심 낮음, 줄 길면 바로 포기 |
| 4 | 재시도형 | `retrier` | 10% | 취소 후 다른 부스 이동, 포기 안 함 |
| 5 | 유령 탐색형 | `ghost_browse` | 7% | 구경만 하고 등록 없이 사라짐 |
| 6 | 유령 등록형 | `ghost` | 5% | 등록 후 취소 없이 사라짐 |
| 7 | 연타형 | `double_tap` | 3% | 버튼 느리면 여러 번 누름 (버그 탐지) |

| 9 | 동시 탭형 | `concurrent` | 2% | 두 탭/기기에서 동시 등록 (버그 탐지) |

> 패턴 1~6: 정상 행동 — LLM 판단으로 다양한 시퀀스 발생  
> 패턴 7~9: 엣지케이스 — 동시성/멱등성 버그 탐지, 페르소나 고정

## 페르소나 목록

### 정상 행동 패턴 (랜덤 배정)

```
1. "급한 성격이다. 순번이 조금만 높아도 답답해하고 더 짧은 곳을 찾아 이동한다."
2. "느긋한 성격이다. 마음에 드는 부스라면 20명이 넘어도 오래 기다릴 수 있다."
3. "합리적인 성격이다. 대기 시간 대비 가치를 따져서 결정한다. 5명 이하면 기다리고, 10명 넘으면 다른 부스를 찾는다."
4. "충동적인 성격이다. 줄이 짧아 보이면 일단 등록하고 본다."
5. "조심스러운 성격이다. 등록 전에 상황을 충분히 살핀다."
6. "포모(FOMO) 성격이다. 인기 있어 보이는 부스에 끌리고, 긴 줄도 기꺼이 선다."
7. "피곤한 성격이다. 5명만 넘어도 그냥 나가려 한다."
```

### 엣지케이스 패턴 (고정 배정)

```
double_tap:  "충동적인 성격이다. 버튼 반응이 느리면 여러 번 누르는 경향이 있고, 줄이 보이면 일단 등록하고 본다."
net_retry:   "급한 성격이다. 앱이 느리면 바로 재시도하고, 축제에서 빠짐없이 체험하고 싶어한다."
concurrent:  "충동적인 성격이다. 여러 탭을 동시에 열어두고 등록 버튼을 누르는 습관이 있다."
```

## 정상 행동 패턴 상세

### 패턴 1 — 대기형 (40%)

**행동 흐름**
- 부스 목록 → 등록 (LLM이 exit하는 경우 드묾)
- 대기 중 → 줄 변화 보며 기다림
- 줄이 전혀 안 줄면 → 다른 부스 추가 등록 시도 (멀티부스)
- 시간이 너무 길면 → 취소 후 재시도

**발견 가능한 문제**
- 순번 폴링 집중 → Redis 부하
- 멀티부스 등록 시 Race Condition

---

### 패턴 2 — 탐색형 (20%)

**행동 흐름**
- 부스 목록 훑어보기
- 대기 인원 적은 곳 발견 시 등록
- 대기 인원 많으면 → 탐색만 하고 이탈 가능

**발견 가능한 문제**
- 부스 목록 응답 느림 → 탐색 경험 저하
- 특정 부스만 줄이 몰리는 불균형

---

### 패턴 3 — 이탈형 (10%)

**행동 흐름**
- 등록 후 순번 확인 즉시 → 높은 확률로 취소
- reason: "이렇게 기다리는 건 못하겠다"

**발견 가능한 문제**
- 취소 후 순번 재배치 정확성
- 이탈률 높은 부스 → UX 개선 포인트

---

### 패턴 4 — 재시도형 (10%)

**행동 흐름**
- 취소 후 다른 부스 상황 보고 → "저쪽 가보겠다"
- 재시도 후 또 이탈 → 반복 가능

**발견 가능한 문제**
- 취소 직후 재등록 시 짧은 간격 중복 처리
- 부스 간 유저 이동으로 대기열 불균형 심화

---

### 패턴 5 — 유령 탐색형 (7%)

**행동 흐름**
- 부스 목록 조회 후 등록 없이 종료

**발견 가능한 문제**
- 실제 전환율 측정에 노이즈 → 탐색 vs 이탈 구분

---

### 패턴 6 — 유령 등록형 (5%)

**행동 흐름**
- 등록 후 취소 없이 종료 (앱 강제 종료 시뮬레이션)

**발견 가능한 문제**
- TTL 없으면 대기열에 영원히 남음 → 스태프가 호출해도 아무도 안 옴

---

## 엣지케이스 패턴 상세

### 패턴 7 — 연타형 (3%)
> "버튼 눌렀는데 반응 없어서 한 번 더"

```
POST /waitings → (100~200ms 후) POST /waitings → (100~200ms 후) POST /waitings
```

**기대 정상 결과**: `[201, 409, 409]`  
**버그 결과**: `[201, 201, 201]` → 중복 등록

---

### 패턴 8 — 네트워크 재시도형 (3%)
> "요청 보냈는데 타임아웃 → 클라이언트 자동 재전송"

서버는 처리 완료했지만 응답 전에 끊김. 클라이언트는 실패로 인식하고 동일 요청 재전송.

**발견 가능한 문제**: 멱등성 없으면 같은 요청 두 번 처리 → 중복 등록

---

### 패턴 9 — 동시 탭형 (2%)
> "같은 계정으로 두 탭/기기에서 동시에 등록 버튼"

```python
await asyncio.gather(
    festin.enqueue(token, booth_id),
    festin.enqueue(token, booth_id),
)
```

**기대 정상 결과**: `[201, 409]`  
**버그 결과**: `[201, 201]` → Redis atomic 연산 실패

---

## 스태프 패턴 (부스당 1명 고정)

**역할**: LLM 판단 없음. 담당 부스 대기열에서 순서대로 호출 반복.

```
POST /waitings/call (booth_id 고정) → [처리 시간 대기] → 반복
대기열 비면 (404) → 짧은 대기 후 재시도
```

**DB**: 로그인 시 `managed_booth_id` 저장됨.

**발견 가능한 문제**
- 빈 대기열 404 처리
- 스태프 처리 속도에 따른 대기열 쌓임 패턴
