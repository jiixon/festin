## 축제 하루 타임라인 (실제 시간 기준)

부스 유형별 피크 타임이 다름. 이걸 시뮬레이션에 반영.

```
시간       트래픽 수준    주요 활성 부스
─────────────────────────────────────────────────────
09:00      낮음          전체 부스 오픈, 탐색형 다수
10:00      중간          포토부스, 만들기 부스 증가
12:00      ★ 피크 1     간식/푸드트럭 폭주
13:00      높음          점심 피크 지속
14:00      중간          포토부스/체험 부스 오후 피크 시작
15:00      ★ 피크 2     포토부스, 만들기/체험 부스 최고점
16:00      중간          오후 피크 감소
17:00      낮음~중간     환승 시간, 탐색형 증가
18:00      중간          저녁 입장 유저 증가
19:00      ★ 피크 3     술/야식 부스 폭주, 이벤트 부스
20:00      높음          저녁 피크 지속
21:00      감소          마감 준비, 이탈형 급증
22:00      종료          잔여 대기열 처리
```

### 부스 유형별 특성

| 부스 유형 | 피크 시간 | 주요 패턴 | 처리 시간 |
|---------|---------|---------|---------|
| 간식/푸드트럭 | 12~13시 | 빠른 회전, 이탈 낮음 | 3~5분 |
| 포토부스 | 14~17시 | 대기 길어도 기다림 | 5~10분 |
| 만들기/체험 | 13~16시 | 가족 단위, 이탈 낮음 | 15~20분 |
| 게임/경품 | 전 시간 | 이탈 높음 | 2~3분 |
| 술/야식 | 18~21시 | 연타 많음, 저녁 스파이크 | 5~8분 |

## 1단계 — 에이전트 검증 (1명)

### 목적
LLM 페르소나 생성 → 에이전트 행동이 자연스러운지 검증.

### 시나리오
```
에이전트 1명 (대기형, 포토부스) 수동 실행
→ Gemini Flash로 파라미터 생성
→ 파라미터대로 Festin API 호출
→ 행동 로그 콘솔 출력
```

### 검증 포인트
- [ ] Gemini Flash가 패턴에 맞는 파라미터를 생성하는가
- [ ] 생성된 파라미터대로 에이전트가 행동하는가
- [ ] API 응답이 상태 업데이트에 정확히 반영되는가

## 2단계 — 패턴 다양성 (14명)

### 에이전트 구성

| 에이전트 | 패턴 | 특이사항 |
|---------|------|---------|
| agent_001~003 | 탐색형 (explorer) | LLM이 부스 비교 후 결정 |
| agent_004~005 | 대기형 (waiter) | 인내심 높은 페르소나 |
| agent_006 | 이탈형 (leaver) | 취소율 검증 |
| agent_007 | 재시도형 (retrier) | 취소 후 재등록 흐름 검증 |
| agent_008 | **연타형** (double_tap) | 페르소나 고정 (충동적), 버그 탐지 |
| agent_009 | **네트워크 재시도형** (net_retry) | 페르소나 고정 (급한), 버그 탐지 |
| agent_010 | 스태프 (staff) | booth_id=4 담당, DB managed_booth_id 저장 |
| agent_011 | 스태프 (staff) | booth_id=5 담당 |
| agent_012 | 스태프 (staff) | booth_id=6 담당 |
| agent_013 | 스태프 (staff) | booth_id=7 담당 |
| agent_014 | 스태프 (staff) | booth_id=8 담당 |

### 검증 포인트
- [ ] 연타형/net_retry에서 중복 등록 발생 여부 (`[201, 201]`)
- [ ] 스태프 부스별 분리 호출 ↔ 방문객 순번 변화 정합성
- [ ] 이탈 → 재시도 사이 Race Condition
- [ ] 스태프 DB 저장 (managed_booth_id 확인)

## 3단계 — 피크 시뮬레이션 (100명 + staff 5명)

### 에이전트 분포 (방문객 100명)

| 패턴 | 비율 | 인원 | 비고 |
|------|------|------|------|
| waiter | 40% | 40명 | 축제 핵심 이용자, 기다리는 사람 |
| explorer | 20% | 20명 | 여러 부스 비교 |
| leaver | 10% | 10명 | 줄 보고 포기 |
| retrier | 10% | 10명 | 취소 후 이동 |
| ghost_browse | 7% | 7명 | 탐색만 |
| ghost | 5% | 5명 | 등록 후 사라짐 |
| double_tap | 3% | 3명 | 연타 버그 탐지 |
| net_retry | 3% | 3명 | 재전송 버그 탐지 |
| concurrent | 2% | 2명 | 동시 탭 버그 탐지 |

staff는 부스당 1명 고정 (+5명).

### 시나리오: 점심 피크 (12:00~13:00)

```
T+0:00   부스 5개에 100명 동시 접속 (오픈 스파이크)
T+0:30   탐색형 퇴장, 대기형/이탈형 혼재
T+2:00   스태프 부스별 처리, 대기열 회전
T+4:00   재시도형 다른 부스로 이동
T+5:00   피크 감소, 잔여 대기열 정리
```

### 관찰 지표
- 대기 등록 p95 < 2000ms
- 순번 조회 p95 < 500ms
- Redis 메모리
- HikariCP connection 사용률
- 에러율 (특히 409, 500)

### 동시성 집중 검증
- [ ] 100명 동시 등록 → 순번 중복 없는지
- [ ] 연타형 3명 동시 연타 → 중복 등록 없는지
- [ ] 동시 탭형 → 같은 유저 이중 호출 없는지

## 4단계 — 장기 운영 (DAU 1000, 1달)

### GitHub Actions 스케줄 운영

서버 비용 없이 GitHub Actions로 각 시간대별 시뮬레이션 실행:

```yaml
# 점심 피크 시뮬레이션 (매일 12시)
- cron: '0 3 * * *'   # UTC 03:00 = KST 12:00

# 오후 피크 (매일 15시)
- cron: '0 6 * * *'   # UTC 06:00 = KST 15:00

# 저녁 피크 (매일 19시)
- cron: '0 10 * * *'  # UTC 10:00 = KST 19:00
```

각 실행마다 해당 시간대 부스 특성에 맞는 에이전트 구성 자동 선택.

### Festin 서버 비용 (t3.micro)
- 상시 가동: ~$8/월
- 낮 시간만 (09~22시): ~$4.5/월
- 스팟 인스턴스: ~$3/월

> **추천**: 스팟 인스턴스 + GitHub Actions 조합. 총 비용 ~$3~4/월.
