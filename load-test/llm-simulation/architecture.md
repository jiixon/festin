# LLM 에이전트 시스템 설계

## 핵심 원칙

**LLM이 판단하고, 코드가 실행한다.**

단순 API 호출은 코드가 처리한다.
"다음에 무엇을 할지"를 결정하는 분기 순간에만 LLM을 호출한다.
이것이 k6와의 차이다 — k6는 분기 없이 스크립트대로만 움직인다.

---

## 전체 흐름

```
에이전트 시작
    ↓
[코드] 부스 목록 조회 (GET /api/v1/booths)
    ↓
[LLM] "이 부스들 중에 등록할까? 어디에?"
    → 판단: "포토부스 등록하겠다" or "구경만 하고 나가겠다"
    ↓
[코드] 등록 실행 (POST /api/v1/waitings)
    ↓
[코드] 15초 후 순번 조회 (GET /api/v1/waitings/booth/{id})
    ↓
[LLM] 순번이 바뀌었을 때만 호출 — "지금 상황에서 어떻게 할까?"
    현재 순번 / 경과 시간 / 줄 변화 속도 / 다른 부스 상황 전달
    → 판단: "기다린다" / "취소한다" / "다른 부스도 등록한다"
    ↓
[코드] 판단대로 실행
    ↓
[LLM] (취소했다면) "다른 부스 재시도할까?"
    ↓
...반복 (최대 40회 × 15초 = 약 10분)
```

> **핵심 최적화**: 순번이 바뀌지 않으면 LLM을 호출하지 않는다.
> 이전 순번과 동일하면 `{"action": "wait", "reason": "대기 유지"}` 를 코드가 직접 반환한다.

## LLM 판단 포인트 설계

### 판단 1 — 등록 여부

```
부스 목록:
- 타코야끼: 현재 대기 3명 (id: 4)
- 즉석 포토부스: 현재 대기 12명 (id: 5)
- 캔들 공방: 현재 대기 8명 (id: 6)

성격: {persona}

어떻게 하겠습니까?

→ {"action": "enqueue"|"exit", "booth_id": 숫자_id|null, "reason": "..."}
```

### 판단 2 — 대기 중 행동 결정 (핵심)

```
현재 상황:
- 대기 중인 부스: 즉석 포토부스
- 현재 순번: 5번
- 대기 경과 시간: 3.2분
- 최근 줄 변화: 줄어들고 있음 (변화량: -2)

다른 부스 현황:
- 타코야끼: 대기 1명 (id: 4)
- 캔들 공방: 대기 6명 (id: 6)

→ {"action": "wait"|"cancel"|"add_second_booth", "target_booth_id": 숫자_id|null, "reason": "..."}
```

### 판단 3 — 취소 후 재시도 여부

```
취소 이유: {cancel_reason}
현재 다른 부스 현황: ...

→ {"action": "retry"|"exit", "booth_id": 숫자_id|null, "reason": "..."}
```

## LLM 클라이언트 설계

**사용 모델**: Groq — `llama-3.1-8b-instant`
- 무료 티어: 500k TPD
- 응답 속도: 빠름 (추론 전용)
- Gemini 2.5 Flash에서 전환 (429 rate limit 및 비용 문제)

**동시 호출 제한**: `asyncio.Semaphore(5)`
- Festin API 호출은 제한 없이 전부 동시 실행
- LLM 호출만 최대 5개로 제한 (rate limit 방지)

**JSON 파싱 전략**:
- 중괄호 depth-counting으로 첫 번째 완전한 JSON 객체만 추출
- 마크다운 코드블록(` ```json `) 자동 제거
- 파싱 실패 시 fallback: 가장 짧은 대기열 부스 선택

**에이전트당 LLM 호출 횟수**:
- 순번이 바뀔 때만 판단 2 호출 → 실제 10~20회 수준 (최대 40회에서 감소)

## 페르소나 설계

에이전트마다 다른 성격을 LLM 프롬프트에 주입한다.

### 정상 행동 패턴 (랜덤 배정)

```python
PERSONAS = [
    "급한 성격이다. 순번이 조금만 높아도 답답해하고 더 짧은 곳을 찾아 이동한다.",
    "느긋한 성격이다. 마음에 드는 부스라면 20명이 넘어도 오래 기다릴 수 있다.",
    "합리적인 성격이다. 대기 시간 대비 가치를 따져서 결정한다.",
    "충동적인 성격이다. 줄이 짧아 보이면 일단 등록하고 본다.",
    "조심스러운 성격이다. 등록 전에 상황을 충분히 살핀다.",
    "포모(FOMO) 성격이다. 인기 있어 보이는 부스에 끌린다.",
    "피곤한 성격이다. 5명만 넘어도 그냥 나가려 한다.",
]
```

### 엣지케이스 패턴 (고정 배정)

LLM이 exit을 결정하면 버그 탐지 코드에 도달하지 못하므로, 등록 의사가 높은 페르소나를 고정한다.

```python
FIXED_PERSONAS = {
    "double_tap": "충동적인 성격이다. 버튼 반응이 느리면 여러 번 누르는 경향이 있고, 줄이 보이면 일단 등록하고 본다.",
    "net_retry":  "급한 성격이다. 앱이 느리면 바로 재시도하고, 축제에서 빠짐없이 체험하고 싶어한다.",
    "concurrent": "충동적인 성격이다. 여러 탭을 동시에 열어두고 등록 버튼을 누르는 습관이 있다.",
}
```

## 결과 로그 샘플

```json
{
  "agent_id": "agent_009",
  "pattern": "net_retry",
  "elapsed_sec": 9,
  "event": "net_retry_enqueue",
  "booth_id": 4,
  "statuses": [201, 201],
  "bug_detected": true
}
```

`reason` 필드가 핵심이다. 이게 쌓이면 "어떤 상황이 이탈을 만드는가"를 텍스트로 분석할 수 있다.

```json
{
  "agent_id": "agent_001",
  "event": "llm_decision_wait",
  "action": "cancel",
  "position": 8,
  "elapsed_min": 4.5,
  "reason": "순번이 거의 안 줄어들고 있고 다른 부스가 더 짧아서 이동하겠다"
}
```

## 프로젝트 구조

```
src/
├── runner.py          ← 메인 실행. 단계별 에이전트 구성, 토큰 발급, 결과 집계
├── agent.py           ← 에이전트 흐름 + LLM 판단 포인트 호출
├── gemini_client.py   ← Groq LLM 판단 요청 (파일명 유지, 내부는 Groq 사용)
├── festin_client.py   ← Festin API 실행
├── config.py          ← BASE_URL, BOOTH_IDS, PATTERN_DISTRIBUTION
└── results/           ← 실행 결과 (.json)
```
