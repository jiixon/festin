# 면접 스토리 가이드

## 핵심 한 줄

> "실유저를 모을 수 없는 서비스라서, LLM이 상황을 보고 판단하는 유저를 직접 만들었습니다."

---

## 왜 이걸 했는가 (동기)

Festin은 실제 축제에서만 쓰이는 서비스라 평소에 실유저가 없다.
유저 없이는 서비스의 문제를 발견할 수 없고, 발견 못 하면 개선도 없다.

k6 부하 테스트는 이미 블로그에 있는 내용이다.
더 근본적인 문제는, k6는 내가 이미 아는 것만 확인한다는 것이다.
"스크립트대로 요청을 N번 보낸다"에서 예상하지 못한 일은 일어나지 않는다.

그래서 **LLM이 현재 상황을 보고 직접 판단하는 에이전트**를 만들었다.
에이전트가 예상하지 못한 행동 시퀀스를 만들고, 거기서 비즈니스 문제가 발견된다.

---

## 무엇을 만들었는가 (구현)

### LLM이 판단하는 시점

매 API 호출마다 LLM을 부르지 않는다.
분기가 필요한 순간, 즉 인간의 판단이 필요한 포인트에만 LLM을 호출한다.
또한 순번이 바뀌지 않으면 대기 중 판단도 호출하지 않는다 — 호출 횟수와 비용 최소화.

```
부스 목록 조회 후 → "등록할까? 어디에?"
순번이 바뀌었을 때 → "기다릴까 / 취소할까 / 다른 부스 볼까?"
취소 후 → "재시도할까?"
```

### 페르소나

에이전트마다 다른 성격을 LLM 프롬프트에 주입한다.
같은 상황(순번 8, 5분 경과)을 보더라도:
- 급한 성격 → "취소하고 다른 부스 가겠다"
- 느긋한 성격 → "조금 더 기다려보겠다"
- 합리적인 성격 → "게임부스가 2명이니 옮기는 게 낫다"

이 다양성이 예상하지 못한 시퀀스를 만들어낸다.

엣지케이스 패턴(연타형, 네트워크 재시도형, 동시 탭형)은 **페르소나를 고정**한다.
이 패턴들의 핵심은 "등록하는 방식"이지 "등록 여부"가 아니기 때문에,
LLM이 exit을 결정하면 버그 탐지 코드에 도달하지 못한다.

### 유저 패턴 9종 (+ staff 고정 배치)

**정상 행동** (LLM 판단):
- 대기형(40%), 탐색형(20%), 이탈형(10%), 재시도형(10%)
- 유령 탐색형(7%), 유령 등록형(5%)

**엣지케이스** (페르소나 고정, 버그 탐지):
- 연타형(3%), 네트워크 재시도형(3%), 동시 탭형(2%)

**스태프**: 부스당 1명 고정. LLM 판단 없이 대기열 순서대로 호출.

### LLM 선택: Groq (llama-3.1-8b-instant)

처음에는 Gemini 2.5 Flash를 사용했으나 Phase 2 10명 시뮬레이션에서 257원이 발생했다.
Groq 무료 티어(500k TPD)로 전환 후 비용 $0로 동일 시뮬레이션 동작.

### 실제 배포 서버에 실제 API 호출

- 배포 서버: `api.festin.shop`
- asyncio + aiohttp로 에이전트 전원 동시 실행
- 결과를 findings-template.md에 기록

### 무인 운영 (Phase 4): cron + 이상치 자동 감지

DAU 1000 한 달치를 시간대별 "파동(wave)"으로 압축해, GitHub Actions cron으로 자동 반복 실행한다. wave마다 점심/오후/저녁 중 시간대를 골라 패턴 비율과 부스 인기도를 다르게 적용 → "점심 food 쏠림", "저녁 drink 연타"가 스크립트 없이 자연 발현된다.

각 wave 종료 후 `wave_report.py`가 지표를 요약하고 임계값(5xx>0, 버그>0, 이탈률>50%, 전환율<30%, LLM 환각>20%)을 넘으면 GitHub 어노테이션을 출력한다. **5xx가 있으면 워크플로우가 fail 처리돼, 내가 안 보고 있어도 장애 알림이 온다.**

## 무엇을 발견했는가 (결과)

### 발견 #1 — net_retry 패턴에서 중복 등록 버그 (Phase 2)

**현상**: 네트워크 타임아웃 재시도 시뮬레이션에서 동일 부스에 500ms 간격으로 2회 요청 → 둘 다 `201 Created`

```json
{"statuses": [201, 201], "bug_detected": true}
```

**원인**: enqueue API에 멱등성 없음. 동일 userId + boothId 중복 처리 방어 로직 부재.

**비즈니스 임팩트**: 실제 유저가 앱 로딩 느려 재시도 시 같은 부스에 2회 등록 가능. 대기열 수 부풀림, 스태프 이중 호출.

**개선 방향**: enqueue 시 중복 체크 추가 (Redis or DB unique constraint)
→ 멱등성 계약으로 수정. 이후 Phase 4 동시성 패턴 49회 시도에도 중복 0건 확인.

### 발견 #2 — 부스 쏠림 (Phase 4, 무인 운영)

**현상**: 점심 파동에서 대기열이 특정 부스로 쏠림. 부스 불균형 stdev 평균 16.6(최대 23.8), 변동계수 CV 최대 0.78 — 한 부스는 텅 비었는데 옆 부스는 줄이 길었다.

**측정**: 부스별 대기열 길이를 30초 간격으로 스냅샷 → wave마다 stdev/CV 집계.

**비즈니스 임팩트**: 서버는 멀쩡한데(5xx 0건) 운영 효율과 유저 경험이 깎인다. 한 부스 앞에 줄이 몰리는 동안 옆 부스 스태프는 논다.

**개선 방향**: 부스 추천/분산 유도 → 개선 전후 stdev 비교로 효과 수치화.

### 발견 #3 — 이탈은 생각보다 늦게 온다 (Phase 4)

**현상**: 평균 이탈 순번이 Phase 3 20.3번 → Phase 4 점심 파동 27.7번. 사람들은 27번째 순번까지 기다리다 포기했다. 이탈률 18.7%(5명 중 1명).

**왜 k6로는 안 나오나**: 이탈 순번이 시간대 맥락(점심엔 더 기다림)에 따라 변한 건, LLM이 상황을 보고 판단했기 때문이다. `if (queue > 5) cancel()` 스크립트로는 고정값밖에 안 나온다.

**개선 방향**: 이탈 순번 분포 → "몇 번째 순번부터 이탈 경고를 띄울지" UX 임계값을 데이터로 결정.

## 면접 질문별 답변 가이드

### "왜 k6를 안 쓰고 LLM을 썼나요?"

k6는 스크립트대로만 움직입니다. 그건 제가 이미 예상한 것만 확인하는 거예요.
이 시뮬레이션의 목적은 **제가 설계하지 않은 상황을 만들어내는 것**입니다.

예를 들어 LLM 에이전트는 순번을 확인한 뒤, 다른 부스 상황까지 고려해서
"저쪽이 더 빠르겠다"고 판단하고 이동합니다.
이 행동 시퀀스는 k6로는 나올 수 없고, 거기서 대기열 이동 시 발생하는
비즈니스 문제나 동시성 이슈가 발견됩니다.

### "LLM 비용이 비싸지 않나요?"

처음에는 Gemini 2.5 Flash를 사용했는데, 10명 시뮬레이션에서 257원이 나왔습니다.
두 가지 최적화를 했습니다.

첫째, 순번이 바뀌지 않으면 대기 중 LLM을 호출하지 않습니다 — 코드가 직접 "대기 유지"를 반환합니다.
둘째, Groq 무료 티어(500k TPD)로 전환했습니다. 현재 LLM 비용은 $0입니다.

### "이탈률은 어떻게 측정했나요?"

각 에이전트가 LLM에게 판단을 요청할 때 `reason` 필드를 기록합니다.
"취소"를 선택한 시점의 순번, 경과 시간, reason을 모아서
"어떤 조건에서 이탈이 발생하는가"를 분포로 분석합니다.

숫자의 정확도보다 **개선 전후 같은 조건으로 비교**하는 게 목적이어서,
상대적 변화가 개선 효과의 근거가 됩니다.

### "실제 유저 행동과 얼마나 비슷한가요?"

완벽히 재현할 수는 없습니다.
하지만 중요한 건 **실제처럼 보이는 것**이 아니라
**내가 설계하지 않은 예외 상황을 만들어내는 것**입니다.
LLM이 상황을 보고 내리는 판단은 제가 미리 짠 코드보다 훨씬 다양한 경로를 만들고,
그 경로에서 발견된 문제는 실제 유저가 겪을 수 있는 문제입니다.

### "실제로 발견한 문제가 있나요?"

세 가지입니다.
Phase 2에서 net_retry 패턴으로 멱등성 버그(중복 등록 [201, 201])를 발견·수정했습니다.
Phase 4 무인 운영에서는 **부스 쏠림**(불균형 stdev 16.6, CV 0.78)과 **이탈 순번 분포**(평균 27.7번)를 발견했습니다. 둘 다 서버 에러가 아니라 운영·UX 문제라 k6로는 안 잡힙니다.
→ findings-template.md / simulation-report-phase4.md 참조

### "서버가 안 터졌으면 의미 없는 거 아닌가요?"

오히려 그게 핵심입니다. Phase 4 8개 wave에서 5xx도 동시성 버그도 0건이었습니다 — t3.micro가 점심 피크를 견딘다는 걸 무인 반복으로 검증한 거죠.
하지만 "에러 없음"은 결과가 아닙니다. 같은 데이터에서 **부스 쏠림**과 **이탈 순번 27.7번**이라는 운영 기준선이 나왔습니다.
즉 이 시뮬레이션은 "장애 감시" 도구가 아니라 **"운영 기준선 발견" 도구**입니다. 서버가 멀쩡해도 제품 개선 포인트는 계속 나옵니다.

## 이력서 문구 예시

**프로젝트 설명**
> 실유저 없는 서비스의 한계를 극복하기 위해 LLM 기반 유저 시뮬레이션 시스템 설계 및 구현.
> LLM(Groq llama-3.1-8b)이 현재 상황(대기 순번, 경과 시간, 다른 부스 현황)을 보고 행동을 결정하는
> 에이전트 9종 × 최대 1000명으로 비즈니스 문제와 동시성 버그를 탐지하고 개선 전후 지표를 수치화.

**성과**
> - net_retry 패턴으로 enqueue API 멱등성 버그 발견·수정 (중복 등록 [201, 201] → 멱등 처리), Phase 4 동시성 패턴 49회 시도 중복 0건으로 재검증
> - GitHub Actions cron 무인 운영 시뮬레이션 구축 — 이상치 자동 감지(5xx/버그 시 워크플로우 fail 알림)로 사람 없이 장애 모니터링
> - 무인 운영 8개 파동(누적 404 에이전트)에서 부스 쏠림(불균형 stdev 16.6, CV 0.78)·이탈 순번 분포(평균 27.7번) 발견 → 부스 분산/이탈 경고 UX 개선 포인트 도출
> - LLM 비용 최적화: 순번 미변동 시 LLM 호출 생략 + Gemini→Groq 전환으로 시뮬레이션 LLM 비용 257원 → $0
